# Agent 项目架构与规范化开发

将 Agent 的"决策"与可验证的业务事实、外部集成和持久化分开，使项目可以安全地扩展、替换依赖并进行回归验证。

## 何时使用

适用于：

- 新建或重构 Agent、工具调用、RAG、评测或 Agent API 项目
- 审查现有项目的目录职责、依赖方向、可观测性或测试边界
- 为 Agent 增加工具、工作流节点、持久化、流式交互或运行治理

**不适用于**：不改变架构边界的单点修复、纯提示词润色，或与 Agent 无关的普通页面功能。不要为了满足目录模板而重构一个简单项目。

## 调用后执行步骤

按顺序完成，不跳过：

1. **识别任务类型**：新建项目 / 审查现有结构 / 增加能力（工具、节点、持久化等）之一
2. **读取现有约束**：找到 `AGENTS.md`、架构文档、运行入口、依赖配置；以已有明确约定为准，不凭目录名判断模块性质
3. **审计运行时归属**：检查打包配置、CI、容器入口、实际 import，确认哪些模块真正参与运行
4. **画出最小数据/控制流**：输入从哪里进入 → Agent 如何决策 → 工具执行 → 结果保存/返回
5. **标明影响范围**：说明本次变更涉及哪些层、哪些层不应受影响
6. **给出结构建议或变更方案**：按推荐结构裁剪，只创建当前范围真正需要的层
7. **输出交付物**（见下方）

若结构性选择改变模块边界、运行入口或数据契约，先更新架构文档和测试计划，再改代码。

## 交付物

根据任务类型输出对应内容：

| 任务 | 交付物 |
| --- | --- |
| 新建项目 | 目录结构 + 各层职责说明 + 依赖方向图 + 初始测试边界 |
| 审查现有结构 | 违反分层原则的具体问题列表（按优先级）+ 修改建议 |
| 增加能力 | 变更涉及的层 + 新模块位置 + 工具 schema 草稿（如适用）+ 需同步更新的测试 |

每次交付都说明：新增代码位于哪个边界、依赖方向是否仍成立、执行了哪些验证、哪些外部集成尚未验证。

## 参考：推荐结构（按需裁剪）

这不是必须照搬的脚手架。单进程或实验项目可以合并相邻层；只有在工具、集成或持久化增长后再拆分。

```text
project/
├── frontend/                    # 可选：页面、流式状态展示
├── backend/app/
│   ├── api/                     # HTTP/RPC、鉴权、SSE、运行记录
│   ├── agent/                   # 状态、图/循环、prompt、终态策略
│   ├── tools/                   # LLM 可见的 typed 工具与注册表
│   ├── services/                # 确定性领域逻辑
│   ├── providers/               # 外部 API、检索等适配器
│   ├── llm/                     # 可替换的 chat/tool-calling gateway
│   ├── schemas/                 # API、工具和领域契约
│   ├── db/                      # repository、事务、迁移模型
│   ├── memory/                  # checkpoint、会话/长期记忆
│   ├── core/                    # settings、composition root / DI
│   └── observability/           # 日志、脱敏、trace/metrics
├── evals/                       # 案例、评估器、回归运行器
├── tests/{unit,agent,api,integration}/
└── docs/architecture.md
```

新项目优先只有一个正式业务源码根。既有项目存在多个源码根时，先核实它们是否都参与运行；确认属于迁移代码后，再标注所有者、移除条件和新代码归属。

## 参考：分层原则

按职责放置代码，不按"方便 import"放置代码：

| 层 | 应负责 | 不应负责 |
| --- | --- | --- |
| API / UI | 协议、鉴权、请求校验、流式传输、用户体验 | 领域计算或直接调用第三方数据源 |
| Agent | 显式状态、LLM 决策、工具循环、终态策略 | 复制领域算法、直连 ORM 或外部 Provider |
| Tools | 面向模型的强类型能力契约和调用边界 | 承载复杂业务规则 |
| Services | 可独立测试的确定性领域逻辑 | 依赖 Web 框架、图编排框架或具体 LLM |
| Providers | 第三方 API、数据库/检索等基础设施适配 | 混入产品决策或提示词 |
| LLM / Memory / DB | 可替换的模型网关、记忆/检查点、持久化 | 泄漏到无关的领域层 |

默认依赖方向：`API / Agent → Tools → Services → Providers`。共享 schema、配置与领域模型应保持窄小且方向清楚。依赖装配集中在一个 composition root / container，避免在业务代码中隐式创建全局客户端。

```text
API ─┐
     ├── Agent ──> Tools ──> Services ──> Providers
UI ──┘       │                 │
             ├── LLM Gateway   └── Domain schemas
             └── Memory / DB

Composition root / container：创建并注入具体实现
```

## 参考：Agent 运行时规范

将 Agent 当作受控运行时，而不是单个聊天函数：

- 用可序列化、大小受控的状态表达消息、`session_id`、`run_id`、步骤数、工具轨迹、核验结果和终态；不要把大型原始文档或数据帧塞进状态。
- 对需要事实的任务采用明确循环：加载上下文 → 模型决策 → 零或多轮工具执行 → 结果核验 → 策略/护栏 → 保存终态。简单问答可以跳过工具。
- 设置总运行超时、最大步骤、单工具超时和有限重试；超时、取消和失败必须成为可观察的终态，不能静默吞掉。
- 将工具失败作为结构化 observation 返回给 Agent 或调用方；不要伪造成功结果以维持对话流畅。
- 多租户、会话或可恢复运行时，按会话和运行隔离 checkpoint、记忆与数据访问范围。
- 只输出面向用户的阶段、工具名、成功状态、耗时和运行标识；不暴露隐藏推理或敏感内容。

核验和护栏应由产品风险决定，将确定性校验、权限判断和高风险动作约束放在代码与工具边界，而非仅寄希望于 prompt。

典型生命周期（按实际风险选择节点，不要添加空节点）：

1. 建立 `run_id`，关联 `session_id`、用户/租户和请求上下文
2. 读取受访问控制的上下文并初始化状态
3. 让模型输出回答或结构化工具调用
4. 验证并执行工具，将成功或失败写为 observation
5. 达到终止条件后，核验外部事实、引用和业务规则
6. 应用必要的终态策略并保存运行状态
7. 返回答案和稳定事件，或返回可诊断的失败终态

生产 checkpoint 不应在未说明的情况下静默降级为内存实现。

## 参考：工具与事实边界

每个模型可调用工具都应具备稳定名称、清晰描述和类型化输入；它应调用 Service，而不是复制业务算法。输出至少表达成功/失败、可消费结果与必要的来源或时效元数据。涉及外部事实时：

- 使用可替换的 Provider 协议或接口
- 明确超时、重试和错误语义
- 失败时如实报告，绝不生成虚构数据
- 工具可用性随租户、角色或产品能力变化时，基于可信的服务端上下文构建工具集；工具执行点仍须二次授权，并为禁用或无权状态返回稳定的结构化错误
- 对敏感、高成本或有副作用的工具，在执行点保留明确的授权检查

新增或修改工具时检查：

- 模型何时应该或不该调用它
- 输入 schema、默认值、枚举与上限是否清楚
- 输出是否包含来源、获取时间、缓存/陈旧状态或推导标记
- 失败、超时、禁用和权限不足是否有稳定的结构化表达
- 是否可以注入 Fake 实现，避免测试依赖真实付费服务

工具名称和描述会影响模型行为；修改它们时，将工具选择视为需要回归验证的对外契约。

## 参考：可观测性与安全

按产品需要定义稳定事件，例如：`run_started`、`run_progress`、`tool_started`、`tool_finished`、`answer_delta`、`run_finished`、`error`。事件关联 `run_id`，可以包含阶段、工具名、成功状态和耗时，但不能泄漏隐藏推理、密钥或私人原文。

长连接需考虑 keepalive、断连取消与终态持久化。日志使用请求关联 ID，并对密钥、token、个人信息及嵌套字段脱敏。需要权限、付费或外部副作用的工具，应在实际执行前落实授权，不能只把限制写进 prompt。

## 参考：测试、评测与交付

优先通过依赖注入使用 Fake Provider、脚本化 Fake LLM Gateway 和内存/临时持久化替身。至少覆盖本次变更涉及的：正常工具循环、无工具路径、工具失败/超时、最大步骤、终态核验或护栏、事件契约，以及租户或会话隔离（如适用）。

| 范围 | 优先验证内容 |
| --- | --- |
| Unit | schema、Service 业务规则、Provider 映射、错误转换 |
| Agent | 无工具/多工具循环、最大步骤、超时、失败 observation、核验/护栏 |
| API | 鉴权、请求校验、流式事件顺序、断连和错误映射 |
| Integration | 迁移、事务、租户边界、checkpoint 恢复 |
| Evals | 工具选择、参数、任务成功、来源、风险表达、延迟、成本 |

将确定性测试与 LLM 评测分开：前者验证代码契约，后者使用可版本化案例；不要仅依赖单一 LLM Judge。
